# Самостоятельная работа №3. Планирование ревьюирования программного проекта

## Цель работы
Закрепить навыки планирования ревьюирования программного проекта, выбора инструментальных средств и организации проверки изменений с использованием системы контроля версий.

**ФИО:** Кухаренко Ксения Станиславовна

**Группа:** ОВКИПо - 301

## 1. Объект ревьюирования

**Объект:** новая версия программного модуля аутентификации и авторизации пользователей (`auth-service`), изменения в которой внесены в отдельную ветвь Git 'feature/auth-v2' перед слиянием с основной ветвью 'main'.

**Почему объект требует проверки:**
- Модуль обрабатывает учетные данные пользователей и напрямую влияет на безопасность системы.
- Изменения затрагивает публичный API (эндпоинты входа, обновления токена, выхода), что может привести к нарушению совместимости с клиентами
- Ошибки в логике проверки прав доступа приводят к несанкционированному доступу к данным.
- Изменения объема (новая логика refresh - токенов, переработанная валидация), поэтому ручной контроль без формализованного плана недостаточен.

## 2. Цель ревьюирования

Цель - убедиться, что новая версия модуля:
- **соответствует требованиям** (ТЗ на аутентификацию: срок жизни токенов, политика паролей, обработка блокировок);
- **корректно реализует алгоритм** проверка учетных данных и обновления токенов,
- **надежно обрабатывает входные данные**, включая недопустимые, граничные и пустые значения;
- **покрыта тестами** для основных и негативных сценариев;
- **понятна и поддерживаема**:читаемые имена, отсутствие дублирования, актуальные комментарии, соблюдение стиля проекта;
- **не содержит критических предупреждений** статического анализа и уязвимостей (секреты в коде, небезопасное хранение паролей).

## 3. Участники процесса

| Участник | Роль и ответственность |
|---|---|
| **Автор изменений** (разработчик) | Подготовка ветви, локальные проверки, написание тестов, оформление запроса на слияние (Pull/Merge Request), исправление замечаний, ответы на комментарии |
| **Ревьюер** (старший разработчик) | Изучение diff, проверка по критериям, фиксация замечаний, повторная проверка исправлений, итоговое одобрение |
| **Ответственный за автоматические проверки** (CI/CD-инженер или дежурный разработчик) | Настройка и контроль прохождения пайплайна (линтеры, статический анализ, тесты), разбор падений CI |
| **Ответственный за интеграцию** (тимлид / мейнтейнер `main`) | Проверка выполнения обязательных условий, разрешение конфликтов, выполнение слияния или возврат на доработку |

## 4. Этапы ревьюирования

| Этап | Ответственный | Действия | Результат |
|---|---|---|---|
| 1. Подготовка изменений | Автор | Создаёт ветвь `feature/auth-v2` от актуального `main`, коммитит изменения малыми логическими порциями с осмысленными сообщениями, пишет/обновляет тесты | Изменения готовы к передаче, история коммитов понятна |
| 2. Предварительные проверки | Автор + CI | Локально запускает линтер, статический анализатор, тесты; пушит ветвь, CI автоматически запускает пайплайн | Пайплайн зелёный либо известны и описаны причины падений |
| 3. Передача на ревью | Автор | Открывает Pull Request (Merge Request) с описанием: что изменено, зачем, как проверять, ссылка на задачу | PR создан, назначен ревьюер, приложен чек-лист |
| 4. Изучение кода | Ревьюер | Читает diff по файлам, сопоставляет с критериями, при необходимости запускает ветвь локально | Замечания зафиксированы или подтверждено соответствие |
| 5. Фиксация замечаний | Ревьюер | Оставляет построчные комментарии в PR, помечает их приоритет (блокирующее / незначительное) | Все замечания оформлены и связаны с кодом |
| 6. Исправление проблем | Автор | Вносит правки новыми коммитами в ту же ветвь, отвечает на комментарии, отмечает resolved | Обновлённая версия запушена |
| 7. Повторная проверка | Ревьюер | Проверяет только исправления и их влияние на остальной код, перезапускает/смотрит CI | Подтверждено устранение замечаний, новых проблем нет |
| 8. Принятие решения о слиянии | Ответственный за интеграцию | Проверяет: все блокирующие замечания закрыты, CI зелёный, есть одобрение ревьюера, нет конфликтов | Изменения слиты в `main` (через squash/rebase по правилам проекта) либо возвращены на доработку |

## 5. Критерии проверки

| № | Критерий | Способ проверки |
|---|---|---|
| 1 | Соответствие требованиям ТЗ (срок жизни access/refresh-токенов, политика паролей) | Сопоставление кода и тестов с пунктами ТЗ, чтение diff, проверка констант и конфигурации |
| 2 | Корректная обработка недопустимых входных данных (пустые поля, неверный формат, SQL/NoSQL-инъекции) | Негативные тесты в наборе, ручной прогон запросов с некорректными данными |
| 3 | Наличие тестов для основных и негативных сценариев, покрытие ключевых ветвей | Отчёт о покрытии (`coverage`), просмотр тестов в PR |
| 4 | Отсутствие критических предупреждений статического анализатора и линтера | Результат CI-пайплайна (0 critical/error), локальный запуск |
| 5 | Отсутствие секретов и чувствительных данных в коде и логах | Статический анализатор секретов (например, gitleaks), ручной поиск по diff |
| 6 | Соблюдение правил оформления кода проекта (стиль, именование, структура модулей) | Линтер с конфигом проекта, ревью diff |


## 6. Выбор инструментальных средств

| Инструмент | Назначение |
|---|---|
| **Visual Studio Code** | IDE для написания и локального просмотра кода, встроенные Git-инструменты, расширения линтера и отладчика |
| **Git** | Система контроля версий: ветвление, коммиты, история изменений, разрешение конфликтов |
| **GitHub (Pull Requests)** | Платформа для открытия PR, построчных комментариев, обсуждения, code review, защиты ветви `main` |
| **GitHub Actions (CI)** | Автоматический запуск линтера, статического анализа, тестов и сканера секретов при push/PR |
| **ESLint / Pylint (по стеку проекта)** | Линтер для проверки стиля и потенциальных ошибок |
| **SonarQube / Semgrep** | Статический анализ: уязвимости, code smells, критические предупреждения |
| **Jest / pytest** | Фреймворк модульных и интеграционных тестов, отчёт о покрытии |
| **gitleaks** | Сканер секретов в коммитах и diff |

## 7. Фиксация замечаний

- Все замечания фиксируются **в Pull Request на GitHub** в виде построчных комментариев (inline comments) к конкретным строкам diff.
- Каждое замечание помечается приоритетом: **blocking** (блокирует слияние) или **minor** (желательно исправить).
- Автор получает уведомление GitHub и видит комментарии в PR; вопрос считается рассмотренным, когда автор ответил и/или внёс правку, а ревьюер нажал **Resolve conversation**.

**Пример корректного комментария ревьюера:**

> **blocking:** В `auth.service.ts`, строка 42: `refreshToken` сохраняется в лог при уровне `debug`. Это утечка чувствительных данных. Предлагаю убрать токен из сообщения лога или маскировать его (`***`). Добавь, пожалуйста, тест, что токен не попадает в лог.


## 8. Исправление выявленных проблем


1. Автор читает все замечания и при необходимости уточняет требования в комментариях.
2. Правки вносятся **новыми коммитами в ту же ветвь** `feature/auth-v2` (без force-push в общую ветвь, если это запрещено правилами; при необходимости — через `git rebase` с предупреждением ревьюера).
3. Сообщение о выполненной работе — ответ в треде комментария: что изменено и каким коммитом (`fixed in a1b2c3d`).
4. Автор нажимает **Resolve conversation** только после того, как правка запушена; окончательное подтверждение устранения даёт ревьюер при повторной проверке.


## 9. Повторное ревьюирование

- **исходная проблема устранена** — сравнение нового кода с текстом замечания, при необходимости повторный ручной прогон сценария;
- **новые ошибки не появились** — просмотр diff исправлений и связанных участков, проверка, что изменения не затронули смежную логику;
- **обязательные автоматические проверки** — CI-пайплайн перезапущен и зелёный: линтер без ошибок, статический анализ без critical, тесты проходят, покрытие не ниже порога, сканер секретов чист;
- **все блокирующие замечания закрыты**, minor — исправлены или осознанно отложены с согласия ревьюера.

## 10. Правила доступа к репозиторию

| Действие | Кто имеет право |
|---|---|
| Изменять код в feature-ветвях | Автор изменений (разработчики команды) |
| Создавать ветви | Разработчики команды |
| Открывать Pull Request | Автор изменений |
| Одобрять изменения (approve) | Ревьюер (минимум 1 одобрение; для критичных модулей — 2) |
| Сливать в `main` | Ответственный за интеграцию (тимлид / мейнтейнер) |
| Прямой push в `main` | **Запрещён** — ветвь защищена (branch protection), только через PR |

Дополнительно: **запрещено** передавать личные учётные данные, коммитить токены, пароли, ключи и файлы `.env` с секретами; сканер секретов в CI блокирует такие коммиты.


## 11. Итоговое решение


Изменения могут быть приняты при одновременном выполнении условий:

1. все **блокирующие** замечания устранены и подтверждены ревьюером;
2. обязательные автоматические проверки (линтер, статический анализ, тесты, сканер секретов) **пройдены**;
3. получено **необходимое одобрение** ревьюера;
4. **нет неразрешённых конфликтов** слияния с `main`;
5. описание PR и тесты актуальны.

При невыполнении любого условия изменения возвращаются автору на доработку.

### Вывод

Предложенный порядок превращает ревьюирование из разовой «вычитки» кода в **управляемый, воспроизводимый и проверяемый процесс**. Разница принципиальна: при стихийном ревью качество зависит от того, сколько времени и внимания нашёл ревьюер, и от того, вспомнил ли он проверить, например, обработку пустого ввода. При формализованном процессе каждый этап имеет ответственного, действие и ожидаемый результат, а значит, проверка не зависит от настроения и загруженности отдельного человека.

**Почему недостаточно только изучения исходного кода.** Человеческое внимание избирательно: ревьюер хорошо замечает логические ошибки и неудачные названия, но плохо и нестабильно — однотипные нарушения стиля, забытые `TODO`, случайно оставленные отладочные выводы, закомментированный код, утечки секретов в логах. Эти дефекты массовые и шаблонные, и именно их эффективнее отдавать машине. Поэтому в плане изучение кода **дополняется**, а не заменяется автоматическими проверками:

- **линтер** снимает с ревьюера споры о форматировании и стиле и не даёт им отвлекать от сути;
- **статический анализ** (SonarQube, Semgrep) ловит потенциальные уязвимости, небезопасные конструкции и code smells, которые трудно заметить глазами в большом diff;
- **тесты** фиксируют, что заявленные сценарии действительно работают, и защищают от регрессий при будущих изменениях;
- **сканер секретов** (gitleaks) закрывает риск, который вручную почти не контролируется, — попадание токенов и паролей в историю коммитов.

В результате ревьюер освобождается для того, что машина сделать не может: **содержательной оценки логики, архитектуры, соответствия требованиям и побочных эффектов реализации**. Это и есть правильное разделение труда между человеком и инструментами.

**Роль системы контроля версий и выбранных средств.** Git и GitHub — не просто «место, куда складывают код», а **несущий каркас процесса**:

- **ветвление** изолирует незавершённые изменения от основной версии и позволяет вести проверку, не блокируя работу команды;
- **Pull Request** становится единой точкой, где сходятся diff, критерии проверки, обсуждение и результаты CI;
- **построчные комментарии** привязывают каждое замечание к конкретному фрагменту кода, а механизм `Resolve conversation` даёт однозначный ответ на вопрос «устранено или нет»;
- **защита ветви `main`** и запрет прямого push гарантируют, что ни одно изменение не попадёт в основную версию в обход ревью;
- **история коммитов и CI-логи** обеспечивают **прослеживаемость**: видно, кто что изменил, когда, по какому замечанию и с каким результатом проверок. Это ценно не только при разборе инцидентов, но и при передаче проекта другому разработчику.

Инструментальные средства при этом не дублируют друг друга, а **образуют конвейер**: линтер и статический анализ проверяют код до и во время ревью, тесты подтверждают поведение, сканер секретов страхует безопасность, а Git/GitHub связывают всё это в единый поток с фиксацией решений.

**Почему обязательна повторная проверка.** Исправления — самый рискованный этап: правя одно, легко задеть смежную логику или внести новую ошибку. Поэтому повторное ревью проверяет не только то, что исходное замечание закрыто, но и то, что **правки не породили новых проблем**, а обязательные автоматические проверки после исправлений снова зелёные. Без этого этапа процесс даёт иллюзию контроля: замечания формально закрыты, но качество итогового кода не подтверждено.

**Итог.** В совокупности предложенный порядок снижает риск включения некачественного или небезопасного кода в основную версию и делает качество изменений **контролируемым на каждом этапе** — от подготовки ветви до решения о слиянии. Процесс опирается не на добросовестность отдельного ревьюера, а на сочетание человеческой экспертизы, автоматических проверок и управляемой работы с изменениями через систему контроля версий. Именно это сочетание — а не один лишь просмотр кода — и обеспечивает надёжный контроль качества программного проекта.
